## 定投（DCA）云端化：跨设备只扣一次 + 手机端执行 + 云恢复

**需求**：定投原只在电脑端本地实现。要求计划与扣款上云，电脑/手机同时登录只扣一次（电脑扣了手机不扣），
在外面只用手机扣费，回来电脑端云恢复即可完全恢复数据。

**选型（用户确认）**：复用已有 GitHub Gist（不接 Supabase 等真后端）+ 计划双向同步（手机也能建/改/删）。

**新增文件**
- `src/api/dcaCloud.ts`：定投云端状态唯一读写出口。**独立 gist**：文件名 `dca-sync.json`、描述 `定投计划云端同步`，
  刻意避开整库备份 gist 的定位规则（文件名不含 fund/backup/持仓、描述不含 基金持仓/AI百万实盘），防止与整库备份互相误覆盖。
  含设备 ID（`dca_device_id`）、30s 缓存、`readDcaCloudState(ttl)` / `writeDcaCloudState()`。

**改造**
- `src/utils/dca.ts`：
  - 确定性交易 id `dcaTradeId(planId,date) = dca_<planId>_<date>` —— 跨设备幂等合并的基石
    （注意 planId 本身也以 `dca_` 开头，所以**绝不能**靠字符串反解 planId，必须显式传入）。
  - 抽出 `executePlanLocal()` 单计划执行体（含「确定性 id 已存在 → 幂等跳过」闸门），
    供纯本地 `executeDueDCAs` 与云端版 `executeDueDCAsCloud` 复用同一套扣款口径。
  - 新增 `executeDueDCAsCloud()`：拉云端 → `reconcilePlans`(合并) → 四分支：
    a) 云端 done → `applyCloudExecution` 幂等恢复（补交易+扣现金+加份额），本机独有已执行的补发云端；
    b) 云端 claimed 他人且未超时(5min) → 本机退避不扣；
    c) 无记录/认领过期 → 认领(claimed) → **二次校验归属** → 本地执行 → 发布 done + 同步计划；
    d) 本机已执行但云端无台账（离线执行后联网）→ 发布到云端；e) 无事可做 → 同步计划。
  - `reconcilePlans` 铁律：配置取 `updatedAt` 较新者；**执行标记取日期较大者**（TODAY-GUARD：
    绝不能让陈旧云端把本地「今天已执行」抹掉，否则刚扣完款会被再次扣）。
  - `DCAPlan` 新增 `updatedAt?`；`addDCAPlan`/`updateDCAPlan` 会打戳。
- `src/utils/storage.ts`：`addTrade` 尊重传入的 id（空串才自动生成）——确定性 id 的前提。
- `src/composables/useFundTrade.ts`：`createTrade` 增加可选 `id` 参数并透传。
- `src/views/DCAPage.vue`：改用 `executeDueDCAsCloud`；增删改计划后 `pushPlansToCloud()`。
- `src/views/PanoramaDashboard.vue`：改 `await executeDueDCAsCloud`；`executed.length || recovered>0` 都刷新 accountCash
  （云端恢复同样扣本机现金）。
- `src/views/Home.vue`：**手机端首次接入定投执行**——`refreshData`(↻) 与 `onRefresh`(下拉) 在持仓估值刷新后执行；
  下拉刷新原本只刷自选/指数/资讯、不刷持仓，已补 `holdingStore.refreshEstimates()`，否则定投会拿昨天的价格。
- `src/components/BackupActions.vue`：payload 增加 `dcaPlans` 完整计划，恢复时 `Array.isArray` 守卫（老备份跳过不清空）。

**关键认知**
- 现金是**每台设备各自 localStorage** 的。跨设备去重保证的是「同一计划当天只被某个设备执行一次」；
  另一台设备从云端恢复时，仍要在自己本机补交易 + 扣自己本机的现金（这是正确的，否则数据不一致）。
- 幂等靠两层：本地 `lastExecutedDate===today` + 确定性 trade id 已存在 → 都跳过。
- 1% 残余风险：两台设备同一秒同时刷新可能各扣一次（Gist 无服务端锁，用户已接受该 tradeoff）。
- **手机端必须也配置 GitHub Token**，否则 `readDcaCloudState` 返回 null → 退化纯本地执行、失去跨设备去重。

**验证**：`npx vue-tsc -b` 退出码 0。

## 定投自动云恢复 vs 手动「云恢复」是否冲突（用户提问，已核实结论：正常情况不冲突）

**结论：不冲突，且能自愈。** 关键前提是 `buildBackupPayload` **同一时刻**快照 trades / cash / holdings，
三者永远一起被替换。加上确定性 trade id 做幂等闸门，两条路径叠加的结果是对的：

- 备份是「定投后」的：restore 带回 DCA 交易 + 已扣的现金 + 新份额 →
  自动链路发现 trade id 已存在 → 跳过。不会重复扣。
- 备份是「定投前」的：restore 把现金/份额/trade 全部复位到定投前 →
  自动链路重新补交易 + 扣一次现金 + 加份额。恰好一次，一致。

**自愈链路已核实**：`applyBackupData` 末尾 `emit('restored')` → 全景 `@restored="() => refreshAll(true)"`
→ 再跑一次 `executeDueDCAsCloud`。所以是「云恢复先生效作为基线，定投再在其上补一次」，语义正确。
另核实 `addOrUpdateHolding` **会落盘**（`saveHoldings(holdings.value)`，stores/holding.ts:568），
所以 DCA 加的份额不会被随后的 `initHoldings()` 冲掉。

**唯一残留风险（非 DCA 逻辑缺陷，是备份不完整）**：非常老的备份**没有 `panoramaAccountCash` 字段**时，
`saveTrades` 会替换交易（DCA 交易消失）但现金**不恢复**（该字段是条件写入，老备份没这字段就跳过）→
自动链路看到 trade 不存在 → 再扣一次 → **现金被扣两次**。根因是那份备份本身残缺，不是定投逻辑问题。
近期备份都带该字段，不会踩到。

**顺手修的显示漏洞**：持仓页(Holding.vue)恢复后状态条数字不刷新 → 新增监听
`window 'backup-restored'` 事件 bump `dcaNavTick`（Home.vue 早已有同类监听）。
