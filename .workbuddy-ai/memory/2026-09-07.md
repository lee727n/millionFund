## 估值取数统一编排：isNav vs dataSource 取舍（仅讨论，未改代码）

用户问「新函数里是不是继续用 dataSource 就好」。结论：**两个都留，分工不同**——
- `dataSource`：保留，但降级为**诊断字段**（日志/排查），调用方禁止用它做判断
- `isNav`：新增，作为**唯一决策字段**

**关键发现：isNav 不能简写成 `dataSource === 'nav'`。**

`fundFast.ts` 有两处把「净值」塞进 `currentValue` 却标成非 nav 的 dataSource：
- `:1730` `currentValue = dwjz`（天天基金的 `dwjz` = 单位净值），`dataSource = 'fallback'`
- `:1740` `currentValue = netValues[code]`（`getFundNetValues()` 存的也是净值），`dataSource = 'local_cache'`

按 `dataSource === 'nav'` 推导会得到 `isNav = false` → UI 显示「估值」、交易弹窗 `isEstimate = true`，属真实错标。
→ **isNav 必须在每个 `currentValue` 赋值点显式设置，与值同步，不能由 dataSource 反推。**

**只剩 dataSource 不加 isNav 的代价**：4 值枚举有「洞」——`'fallback'`/`'local_cache'` 既不等于 `'nav'` 也不等于 `'estimate'`（grep 确认：这两个值全项目只有写入、没有任何读取判断）。
洞的存在逼出 Detail.vue:323-332 / Home.vue 同款第三个「日期兜底」分支，也是 Detail.vue:302、Home.vue:530 写 `=== 'estimate'` 而非 `!== 'nav'` 的原因。

## getTradingDateStr 的 9 点位移是真 bug（未修）—— 附我自己的一次误判更正

`utils/navDate.ts:13-17`：`hour < 9 → target = date - 24h`。

> **更正**：我一度以为修法是「减一天时跳过周末」（复用 `getPrevWorkdaySync`）。**这是错的** ——
> 周二~周五早上，上一工作日就是昨天，改完结果一模一样；周一早上反而从「碰巧正确的 false」
> 变成「危险的 true」。真正的修法是**去掉 9 点位移**。

行为表（最新 navDate 取上一交易日）：

| 时刻 | 真实今天 | 现在 today | navDate | 现在 navIsCurrent | 正确 |
|---|---|---|---|---|---|
| 周二 08:00 | 周二 | 周一 | 周一 | **true** ✗ | false |
| 周三 08:00 | 周三 | 周二 | 周二 | **true** ✗ | false |
| 周一 08:00 | 周一 | 周日 | 周五 | false ✓ | false |
| 周二 10:00 | 周二 | 周二 | 周一 | false ✓ | false |
| 周二 20:00 | 周二 | 周二 | 周二 | true ✓ | true |
| 周六 10:00 | 周六 | 周六 | 周五 | false ✓ | false |

即：**工作日 00:00–09:00 这个窗口（周一除外）navIsCurrent 恒为 true，是错的。**
根因：位移后 `today` = 昨天，而昨天的净值已经公布了，于是「昨天的净值」被当成「今天的净值」。

后果链（Detail.vue:121 / TradeCenter.vue:130）：
1. `!data.navIsCurrent` 守卫被跳过
2. `updateTradesByCode` 的 `shouldUpdate = t.estimated || t.date === navDate` 对 estimated 交易无条件确认
3. → 今天(T 日) 08:00 的交易被 T-1 的净值确认，**份额算错**
4. 更糟：`!holdingConfirmedUpdated` 那一半用的是 `holding.isUpdated`，而它走的是**同一个错误公式**
   → 两层保险被同一个根因一起污染，只修 navIsCurrent 不够

连带小问题：`fundFast.ts:1621` `isHolidaySync(today)` 在 0-9 点查的是昨天，节假日判断会错。

**修法 A（推荐）**：去掉位移，`today` 恒为真实今天。副作用需补偿 ——
`fetchNetValueHistoryFast` (566/585) 的 `hour >= 9 && hour < 18` 窗口不覆盖 0-9 点，
会导致早上每次穿透重新拉净值历史，需改成 `hour < 18`；`isUpdated` 在 0-9 点全 false，
早间刷新会多调一次 API（与 9 点后的行为一致，非新增负担）。

**修法 C（最小改动）**：保留 `getTradingDateStr` 现语义（服务缓存/交易日归属），
新增 `getNavCheckDate()` = 真实今天，只给 `isNavUpToDate` 用。改动面最小，但留下两套日期口径。

## 全景大屏交易记录：按「交易日」过滤（不是自然日）

用户诉求：「今天周一，想看上周五交易了什么」。这暴露了一个坑——

**核心决策：交易记录的时间过滤一律按「实际有交易的日期」倒序，绝不用自然日区间。**

- 原因：周一选「近3天（自然日）」= 09-07/09-06/09-05，**上周五 09-04 反而被排除**，
  而周六周日不可能有交易，白白占掉区间名额。交易场景用自然日过滤天然错配。
- 实现：`tradeDateStats` 从 `allTradesWithReturn` 统计出「有交易的日期 + 条数」倒序数组，
  一切区间/快捷项都基于它取前 N 个，周末和节假日自动对齐，无需查节假日表。

下拉框四层（`tradeFilter` 取值）：
| 值 | 含义 |
|---|---|
| `all` | 全部 |
| `recent3` / `recent5` | 近3 / 近5 个**有交易的日期**（不是自然日） |
| `prev` | **上一交易日** = 严格 `< 今天` 且有交易的最近一天（周一 → 上周五） |
| `'YYYY-MM-DD'` | 精确某天（从只含有交易日期的列表里选，不会点空） |

- `prevTradeDate` 用 `date < getCalendarDateStr()` 比较字符串（YYYY-MM-DD 字典序=时间序）。
  如果今天已下单，今天不算「上一」；周一时若周五没操作会自动继续往前找。
- 按钮上直接显示落点，如「上一交易日 09-04」，不用点开才知道选到了哪天。

  面板计数也跟着改成 `filteredTrades.length`，过滤后能看出筛出几条。
