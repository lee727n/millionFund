## QDII 持仓「显示估值涨幅而非真净值」根因 + 修复

现象：用户截图 — 024239 华夏全球科技先锋混合(QDII)C，broker 显示 9/15 真实净值 -3.77%，
App 却显示 -3.24%（其实是 9/15 盘中的估值涨幅）。用户原话：「3.24% 哪里来的，是接口拿的最新净值吗？」

### 排查过程

1. **接口实测**：pingzhongdata 024239 最新一条 `{"x":1789315200000,"y":2.5368,"equityReturn":-3.77}`（9/15 真净值 -3.77%）；fundgz 024239 返回 404（QDII 没有官方实时估值）。
2. **本地持仓**：valueDate=9/14、todayChange="-3.24"、currentValue=2.4546（估算值）—— 9/15 盘中 fundgz 404 后 App 用重仓股价算的估算落盘。
3. **9/15 收盘后基金公司公布 9/15 NAV (-3.77%)**，但 App 没刷到。

### 真因：我的第一版修复用了进度条口径 `getProgressDateStr()`，早 09:00 前误判

上一轮我加了 `holdingNavIsCurrent(h)`，但 today 传了 `getProgressDateStr()`：
- 现在是 2026-09-16 0:50 → `getProgressDateStr() = 2026-09-15`
- QDII 判定：`valueDate(9/14) === prevWorkdaySync(9/15) = 9/14` → **TRUE** → 跳过 API → 回灌 -3.24%

进度条口径是**故意**为 UI 设计的宽限期（早上 9 点前当昨天还在交易，进度条不空），
但**跳过 API 的闸门不该用宽限期**——自然日口径才是「这是不是已经该公布的那期净值」的正确判断：
- 自然日 = 9/16，QDII：`prevWorkdaySync(9/16) = 9/15`
- `valueDate(9/14)` 既不是 9/16 也不是 9/15 → **不 current** → 重拉 → 拉到 9/15 净值 -3.77% ✓

### 修复

`src/stores/holding.ts` 和 `src/composables/useFundValuation.ts` 两处 `holdingNavIsCurrent`：
- **去掉 `today: getProgressDateStr()`**，让 `isNavUpToDate` 用默认的 `getCalendarDateStr()`（自然日）
- 同时 `useFundValuation.ts` 删掉不再使用的 `getProgressDateStr` import
- 注释里写明「必须用自然日，不能用进度条」+ 真实案例链接，避免下次再踩

`npx vue-tsc -b` 通过。

### 衍生教训（更新进 MEMORY.md）

- **进度条口径 vs 自然日口径要严格区分**：
  - `isUpdated`（UI 徽标，进度条用）→ 显式传 `getProgressDateStr()`（保留宽限期）
  - **`holdingNavIsCurrent`（跳过 API 闸门）→ 必须不传 today（自然日）**
  - 同是 `isNavUpToDate` 调用，不同口径导致行为差异巨大，注释必须写清用途。

## Request 7：-0.08% 又冒出来（非交易时间被旧估值覆盖）

现象（凌晨 0:56，自然日修复之后）：App 把 024239 显示成 **-0.08%**，而不是真净值 -3.77%。

### 真因：estimate 分支缺 `inTradingTime` 守卫

自然日修复后，App 确实去重拉了，但 `fetchFundAccurateData` 的估值分支写的是：

```
} else if (isWeekday && result.estimate > 0) {
```

**没有 `inTradingTime` 限定**。凌晨 0:56 是工作日但非交易时间，于是命中这个分支：
- 缓存里的 `estimate` 是 9/15 盘中（fundgz 对 QDII 404，App 用重仓股重算的快照）留下的 **-0.08%**
- 非交易时间根本没有「今日实时估值」，却拿上一交易日的盘中快照当今日涨跌幅 → 盖掉了刚拉到的 9/15 真净值 -3.77%

### 修复

`src/api/fundFast.ts` 估值分支改为 `else if (isWeekday && inTradingTime && result.estimate > 0)`：
- 仅「交易日 + 盘中 + 净值未更新」才用实时估值；
- 非交易时间（盘前/盘后/半夜）落空 → 走下面的 prev-NAV 分支（`result.nav`/`navChange`），正确显示最新已公布净值；
- QDII 024239 凌晨也走 prev-NAV → 显示 -3.77%（9/14 发布、9/15 那期，QDII 延迟）。

`inTradingTime = isWeekday && isTradingHours`，`isTradingHours`=9:30-11:30 ∪ 13:00-15:00（fundFast.ts L1660-1664）。

`npx vue-tsc -b` 通过（exit 0）。

### 衍生规律（已是第二层守卫）

「跳过 API 闸门」用自然日（`holdingNavIsCurrent`）解决「跨天不重拉」；
「取数后分支」用 `inTradingTime` 解决「非交易时间误用旧盘中估值」。
两者是不同环节的守门员：前者决定要不要拉，后者决定拉到后选哪条数据。排查「非交易时间显示了一个奇怪的小涨跌幅」先查 estimate 分支有没有 `inTradingTime`。

## Request 8：华宝纳斯达克「数据对、却一直绿（未更新）」

现象（2026-09-16 01:08，盘前）：华宝纳斯达克实际用的是最新净值、涨跌幅也对，但全景基金名是绿色、
更新进度条也显示「未更新」。其他 QDII 都正常（绿色消失、已更新）。

### 真因：快路径不回写 `isUpdated`，绿色/进度条靠它驱动

- 绿色 `fm-pending`、进度条「未更新」全部读 `holding.isUpdated`（`PanoramaDashboard.vue:1083`、
  `Home.vue:1133`、`Holding.vue:895`）。
- `isUpdated` 唯一写入点是 `updateHoldingWithAccurateData`（按进度条口径 `getProgressDateStr()` 算），
  它只在**慢路径**（真调 API）和 `refreshEstimates` 的「已更新」分支里被调用。
- `useFundValuation.loadFundData` 的**快路径**只复用 holding 数据、直接 `return`，**从不回写 `isUpdated`**。
- 我上一轮的「自然日修复」把快路径闸门从 `holding.isUpdated` 换成了 `holdingNavIsCurrent`（自然日，与 isUpdated 脱钩）。
  于是：华宝纳斯达克加载时 valueDate 已是当前 → 命中快路径 → 数据正确，但 `isUpdated` 停在旧持久值 `false` → 绿。
  其他 QDII 加载时 valueDate 还旧 → 走慢路径 → `updateHoldingWithAccurateData` 把 `isUpdated` 置 true → 不绿。
  所以是「看哪个基金这次恰好走了慢路径」的偶然结果。

### 修复

`src/composables/useFundValuation.ts` 快路径里，复用数据后按进度条口径重算并写回 `holding.isUpdated`：
```ts
holding.isUpdated = isNavUpToDate({
  nav: holding.currentValue,
  navDate: holding.valueDate || '',
  isQDII: holding.isQDII === true,
  today: getProgressDateStr()
})
```
能进快路径（holdingNavIsCurrent 自然日 true）就说明 valueDate 是当前这一期 → 进度条口径也必为 true，无假阳性。
顺带 `updateTradesByCode(..., !!holding.isUpdated)` 也用上了刷新后的 true（之前用旧 false 会导致该基金交易不被确认）。
导入补了 `getProgressDateStr`。`npx vue-tsc -b` 通过（exit 0）。

### 规律（写进 MEMORY.md 刷新短路 #1）

`holdingNavIsCurrent`（快路径闸门）和 `holding.isUpdated`（UI 状态）是两个字段：
- 快路径只保证「数据是最新的」，但**必须自己回写 `isUpdated`**，否则 UI 状态会 stale。
- 凡改快路径闸门逻辑，都要确认 `isUpdated` 仍被正确刷新。

## Request 9：华宝纳斯达克 绿名 + 进度条 17/18（QDII 手动开关漏勾）

现象（2026-09-16 01:18，盘前）：上一轮快路径补 `isUpdated` 后，**仍**有 1 只（华宝纳斯达克 017436/017437，QDII-普通股票）绿名、进度条 17/18。
数据（最新净值/涨跌幅）是对的，其他 QDII 都正常。

### 真因：`isQDII` 之前只靠持仓「手动开关」，漏勾就被当普通基金 → 时差判定全错

- 绿色 `fm-pending`、进度条 `isUpdated` 的判定链：`getFundNameClass`/`updateProgress` → `holding.isUpdated`
  → `updateHoldingWithAccurateData` 里 `isNavUpToDate(navDate, isQDII, 进度条口径)`，其中 `isQDII = h.isQDII`（**持仓手动开关**）。
- 而 `fetchFundAccurateData` 自己的 `isNavUpdated`/`navIsCurrent` 也用传入的 `isQDII` 参数（同样是手动开关），
  真正的 `checkIsQDII`/`fundType` 推导只存在于 `fetchFundEstimateFast`，根本没进估值/更新判定。
- QDII 净值滞后 T+1/T+2：华宝纳斯达克实际是 QDII 但持仓 `isQDII=false` → 严格匹配要求 `navDate === 今天(9/15)`，
  可它最新净值停在 9/14（QDII 滞后）→ `isNavUpToDate` 返回 false → `isUpdated=false` → 绿，尽管显示的就是最新净值。
- 逻辑上：任一只「真 QDII 但漏勾开关」的基金都会这样；华宝只是恰好那只。

### 修复（让 QDII 判定用接口权威值，不再依赖手动开关）

1. `fetchNetValueHistoryFast` 加载 `pingzhongdata/{code}.js` 时本就有 `Data_fundType`，
   顺手推导 `isQDII`（`includes('QDII'|'qdii'|'海外'|'全球')`）并回传（不额外发请求）。返回类型加 `isQDII?: boolean`。
2. `FundAccurateData` 加 `isQDII: boolean` 字段；`fetchFundAccurateData` 里
   `effIsQDII = historyResult.isQDII ?? isQDII(参数)`，用于 `isNavUpToDate`（isNavUpdated/navIsCurrent）并写进 result。
3. `updateHoldingWithAccurateData`：`isQDII = data.isQDII ?? h.isQDII`（权威优先），
   且把 `isQDII: data.isQDII ?? h.isQDII` 写回持仓——漏勾的 QDII 自动纠正（顺带修好 QD 角标/快路径闸门）。
4. `refreshEstimates`「已更新」分支补 `isQDII: holding.isQDII` 以过类型（走慢路径的基金由 fetchFundAccurateData 带真值）。

`npx vue-tsc -b` 通过（exit 0）。所有漏勾的 QDII 下次刷新即走慢路径→纠正→绿名消失、进度条满。
用户需重建/热更 App 才能生效。

### 规律（写进 MEMORY.md）

QDII 判定**按用户设计用持仓手动开关**，不要自动从接口 `fundType` 推导去覆盖手动开关。
`isUpdated`/`navIsCurrent`/`holdingNavIsCurrent` 都吃 `isQDII`，漏勾开关会让 QDII 滞后净值永远 != 今天 → 误判「未更新」。
**本 Request 加的接口自动推导 + 写回持仓 已在用户确认后回退**：用户明确「还是通过手动标记判断是不是 QDII」。
教训：改动判定逻辑前先确认设计意图——用户要的是手动开关，自动覆盖是反模式。

## Request 11：全景/持仓跳进 .detail 点「来源/行业板块」误报「暂未持有该基金」

现象（2026-09-16）：从全景大屏或持仓页跳转到 `/detail/:code`，页面能正常显示基金净值，但点底部「来源」「行业板块」按钮弹出 `暂未持有该基金`（`manageSource`/`manageSectors` 里 `holdingInfo.value` 为 null 的守卫）。

### 真因：`holdingStore.initHoldings()` 在 Detail 页从不调用

- `initHoldings` 在 `main.ts` 启动时不调用，只被 Home/Portfolio/Holding/Panorama/StarKLine 这几个 view 的 onMounted 调用。
- `Detail.vue` 自身 **从不调用** `initHoldings`。
- 全景的 `goDetail()` 用 `window.open('/detail/CODE', '_blank')` 开**新标签页**，新标签页里只有 Detail 挂载 → `holdingStore.holdings` 仍是初始空 `[]` → `holdingInfo` 计算属性 `holdings.find(h => h.code === fundCode)` 命中不了 → 误报未持仓。
- 净值仍正常：净值走的是按 code 调接口的 `loadFundData`，与 holdings 无关，所以页面看着是好的。

### 修复

`src/views/Detail.vue` 的 `onMounted` 里，加载数据前若持仓尚未初始化则先 `initHoldings()`：
```ts
if (holdingStore.holdings.length === 0) {
  await holdingStore.initHoldings()
}
await loadFundData()
```
用 `length === 0` 守卫：in-app 从已初始化过的持仓页进来时不重复拉全部基金；新标签页/深链/刷新（store 为空）时才初始化。

`npx vue-tsc -b` 通过（exit 0）。

### 规律

凡是可能被 `window.open` 新标签页或深链直达的 view，都要**自己**保证所依赖的 store 已初始化——不能假设路由链路上某个上游 view 已经调过 init。Detail 是被 `window.open` 的常客，最容易踩这个坑。

## Request 12：估值/净值选择逻辑回归——午休+盘后也该用估值（inTradingTime 太严）

现象（2026-09-16 午）：昨天 Request 7 给 `fetchFundAccurateData` 估值分支加的 `inTradingTime` 守卫（= 9:30-11:30 ∪ 13:00-15:00）太严，
导致**午休 11:30-13:00** 和**收盘后净值公布前 15:00-~18:00** 都不再走估值分支，回退成上一期净值——用户要的是这两段仍用估值。

### 修复（fundFast.ts `fetchFundAccurateData` 内）

新增 `estimateWindow = isWeekday && (currentHour > 9 || (currentHour === 9 && currentMinute >= 30))`
（即「交易日且已过开盘 ≥9:30」），把估值分支条件从 `isWeekday && inTradingTime && estimate>0` 改成 `isWeekday && estimateWindow && estimate>0`。

语义区分（两个不同概念，别混）：
- `inTradingTime`（严格交易时段 9:30-11:30/13:00-15:00）：只在第三分支「估值拉取失败时的兜底」用（`if (inTradingTime) currentValue=0 保持旧市值，否则回退 prev NAV`）。
- `estimateWindow`（≥9:30 的交易日）：估值可用窗口，**覆盖盘中+午休+盘后净值公布前**。
- 盘前（<9:30，含凌晨/清晨）：`estimateWindow`=false → 走 prev NAV 分支，用上一期已公布净值（避免 Request 7 的 -0.08% 盖 -3.77% 事故）。
- 净值公布后第一分支 `isNavUpdated` 优先用净值；`estimateWindow` 只在「净值未更新」时生效。

用户明确：**凌晨「算成凌晨前这一天判断净值是否更新」的那套 `getProgressDateStr`/prevWorkday 逻辑已经有了，不要乱改**——本修复完全没碰 `isNavUpToDate`/`navIsCurrent`/`holdingNavIsCurrent`，只改了估值分支的可用窗口。

## Request 14：全景「调整成本」盘后改了市值，刷新浏览器又变回原数（总市值永远加不上去）

现象：盘后 17:29 在「调整成本」弹窗把某基金市值设成 3W，点确认页面变 3W，但**刷新浏览器**又变回原来的 2.04W；改了好多只基金刷新全被还原，总市值恒为 190W 加不上去。

### 真因：`submitCostAdjust` 用 `accurate.nav` 算份额，但显示/重算用的是 `currentValue`（估值）

- 持仓市值恒等于 `shares × currentValue`（`updateHoldingWithAccurateData` L296-298 每轮重算，持仓 `marketValue` 字段不参与显示）。
- 盘后净值未公布时：`accurate.nav` = **上一期净值（昨净值）**，`accurate.currentValue` = **当天估值**。两者不相等（例：nav=1.5，estimate=1.02）。
- 旧代码 `latestNetValue = accurate.nav`，于是 `newShares = 3W / nav = 20000`（= 原份额！）。虽然当时把 `currentValue` 也设成 nav=1.5 让页面瞬时显示 3W，但**刷新后** `updateHoldingWithAccurateData` 用真正的 `currentValue`(=估值1.02) 重算 → `20000 × 1.02 = 20400 = 2.04W`，缩水回原数。
- 因为份额根本没变（还是原数），总市值自然永远加不上去。

### 修复（`src/views/PanoramaDashboard.vue` `submitCostAdjust`）

份额换算改用 `accurate.currentValue`（当前用于显示/重算的那个价格），不再用 `nav`：
```ts
if (accurate && accurate.currentValue > 0) {
  latestNetValue = accurate.currentValue
  latestDate = accurate.navDate || accurate.estimateTime || ''
} else if (accurate && accurate.nav > 0) {
  latestNetValue = accurate.nav   // 兜底
}
```
盘后未出净值 → `currentValue=估值`，`newShares = 3W / 估值 = 29411`，刷新后 `29411 × 估值 = 3W`，**稳住**；净值已公布时 `currentValue=nav` 两者一致，行为不变。
`buyNetValue/costNetValue/addedGain` 跟着同一个 `latestNetValue` 走，利润口径也自洽。

写纯 JS 复刻验证：旧逻辑新份额=20000（→刷新 2.04W ❌），新逻辑新份额=29411（→刷新 3W ✓）。`npx vue-tsc -b` 通过（exit 0）。

### 规律（写进 MEMORY.md：调整成本/份额换算）
- **调成本/调份额换算价格基准必须 = `accurate.currentValue`**，不能用 `accurate.nav`。盘后未出净值两值不等，用 nav 算出的份额会在刷新被按估值重算后缩水回原值。
- 持仓 `marketValue` 是**派生量**（shares×currentValue），手动设的 `marketValue` 字段会被每轮 `updateHoldingWithAccurateData` 覆盖；要改市值本质是改 `shares`。

## Request 15：用户纠正 Request 14 的诊断 —— 不是价格口径误差，是「份额没保存/录入陷阱」

用户原话：刷新后市值又变回 1W，等于加的份额没加上、没保存上；**不是**「用昨天还是今天的值算出来的误差」那种小偏差，是份额整段没加上。

### 真因（与 Request 14 结论不同，以用户为准）

1. **份额其实每次都落盘了**（`addOrUpdateHolding` → `saveHoldings` 全量写；`updateHoldingWithAccurateData` 也保留 `shares`）。静态追完整条链路没有「丢份额」的点。
2. **真正的触发器是录入语义陷阱**：`openCostDialog` 用 `holding.marketValue`（旧市值）预填「持仓市值」输入框，且该字段是 **REPLACE 不是 ADD**。用户支付宝加仓后，把「新增的那 1W」当成调后总市值填进去（应该填「新的总市值 2W」）。于是 `newShares = 10000/nav = 8000 = 旧份额` → 刷新后 MV 还是 1W。用户眼里就是「份额没加上」。
   - 例：旧 shares=8000，nav=1.25 → 旧 MV=1W；支付宝加仓后总 MV=2W。填 10000（新增额）→ newShares=8000 → 刷新 MV 仍=1W。✅ 完全复现用户描述。
3. Request 14 的 currentValue 口径只对「填对了新总市值」的人有效（MV 能稳住），但**用户要的是按支付宝口径（昨日净值）算份额**，且根本痛点是录入陷阱导致份额没变。

### 修复（PanoramaDashboard.vue `submitCostAdjust` + 弹窗）

1. **价格基准回退到 `accurate.nav`**（与 Home / Detail 两个入口一致，符合用户「用昨日净值、和支付宝对得上」的诉求）。`accurate.nav>0` 优先，`currentValue` 仅作兜底。
2. **落盘 `valueDate` / `isNav:true` / `isUpdated:true`**：之前 `submitCostAdjust` 不写 `valueDate`，导致编辑后 valueDate 停在旧值 → 下次刷新 `holdingNavIsCurrent` 判非当前 → 走慢路径用今天实时值重算 marketValue/profit，把刚录的值覆盖，看起来像「没保存」。补齐后净值已公布的常见场景 valueDate=今天 → 快路径原样复用，编辑稳稳保留。
3. **弹窗加「预计份额」实时预览**：`openCostDialog` 预取最新 nav 存 `costBasisNetValue`，`costPreviewShares = 调后市值 ÷ nav` 实时显示。用户录入前就能核对份额是否合理（填成新增额时预览会明显不对），从源头杜绝录入陷阱。字段标签也改为「调后持仓市值」并注明「请输入支付宝上的最新总市值」。

## Request 16：调成本公式「份额 vs 实盘账户」差异根因 —— 实盘是交易流水累计，我们是快照公式

用户截图两张（图 1 = 我们的调成本对话框，图 2 = 支付宝实盘），问「看看他是怎么算的 为什么我们的算出来的和实际持仓份额不同」。

### 实测数据（016702 银华海外数字经济 QDII）

| 来源 | 持有资产 | 累计收益 | 持有份额 | 最新净值 | 单位成本 | 持仓成本 |
|---|---|---|---|---|---|---|
| 我们的对话框（图 1） | 158,711.32（用户填） | 11,961.32（用户填） | **77,344.70**（公式 `MV÷NAV`） | 2.0520 | — | — |
| 支付宝实盘（图 2） | 158,711.32 | 11,961.32 | **76,370.04** | 2.0520 (09-15) | 1.8954 | 144,750.00 |

两份金额完全一致；**份额差 974.66 份**，乘以净值正好 ≈ **2,000 元**。

### 实盘账户怎么算的份额

**交易流水累计**：每一笔申购 `shares += (amount − 手续费) ÷ NAV_at_purchase`，每一笔赎回扣减。**「处理中」/待确认的资金不计入份额**（图 2 底部「2笔资金处理中」就是证据）。红利再投则按除权日 NAV 加到份额。

校验：
- 1.8954 × 76,370.04 ≈ 144,751.7 ≈ 144,750（持仓成本，含四舍五入误差）✓
- 158,711.32 − 144,750 = 11,961.32（持仓收益）✓
- 全闭环对得上 → 76,370.04 是「**已确认累计**」的真份额。

### 我们怎么算的份额 ——「快照公式」

```ts
shares = marketValue / latestNAV   // 当前实现
```

假设「今天的市值就是持有 X 份按最新净值 X 折算」得到的，X 反推即可。**前提是「市值里不包含任何还未落账的钱」**。

但用户的 MV 158,711.32 是支付宝**实时**显示的，里面**包含**那 2 笔「处理中」的 2,000 元 —— 而支付宝的 76,370.04 **不含**这 2,000 元：
- 公式：`158,711.32 / 2.0520 = 77,344.70`（把处理中也折成份额了）
- 真账户：`76,370.04`（处理中不入份额）
- 差值：`974.66 × 2.0520 ≈ 2,000 元`（**正好**就是处理中金额）

### 其它让两边分歧的因素

- **申购费**（通常 0.1~0.15%）：基金公司扣费后入账，真实份额 < `金额÷NAV`。我们的快照公式**忽略**手续费，会高估份额。
- **红利再投**：MV 不变但份额会涨；快照公式**低估**份额。
- **跨日估值**：我们用 `latestNAV`（通常是昨净值，盘后没出今天净值）；支付宝 MV 的口径也是同一净值所以一般对得上，但若支付宝用了盘后实时估值就会差。

### 关键含义

我们的 `shares` **不是真份额**，是「如果按最新净值把 MV 全部还原、应该得到多少份」的**合成值**。日常跟踪市值/盈亏不影响（`marketValue = shares × currentValue` 恒成立），但：
- **处理中的钱确认入账后**，真份额会变，我们不跟 → MV 永远比真账户少 2,000 元（除非用户再调一次）。
- **做T、拆账、对比真实份额、跟其它账户对账** 时都不准。
- **视图里的「持仓份额」字段**展示的是合成值，对账时要解释「这是公式份额、不是交易份额」。

- 填了 → **以它为准**，反推 `单位成本 = (MV − profit) ÷ shares`，并持久化该 `shares`。

这样：

- 有处理中 / 想要精确对齐支付宝 → 直接粘 76,370.04，反推出的 `单位成本 1.8954` 也和支付宝一致。
