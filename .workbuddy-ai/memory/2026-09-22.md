## 批量导入「用昨天净值 + 买点落昨天」bug 修复（008984 财通科技创新复现）

用户反馈：今天(9.22)用「我的持仓-批量」功能加 008984，累计 -1.39% 等于今天估值涨幅、买入点落在 9.21——疑似用昨天净值添加。

**根因**：`Holding.vue batchImport` 直接用 `fetchFundAccurateData` 的 `nav`/`navDate`（上一期已公布净值）当买价、`estimated:false`、`buyDate:navDate`。交易时间净值未出时 nav=9.21 的净值、navDate=9.21 → 份额按昨天净值算、买点标 9.21，累计=(今天估值-昨天净值)/昨天净值≈今天估值涨幅。与之前 3 只京东基金的单加老路径是同一类 bug，但批量路径没走 `resolveAddValue`。

**修法**：
- `Holding.vue batchImport`：改用 `resolveAddValue(accurateData)` 拿买价/estimated（净值未出用盘中估值、出则用今日净值），`buyDate` 与交易 `date` 统一用 `getCalendarDateStr()`（今天），`estimated` 透传给 `createBuyTrade`。
- `useFundTrade.getTodayFirstBuyCorrection` 签名扩参 `(hShares, holdingBuyNetValue, dayPrice)`，改用「白天买入价→正式净值」价格因子等比缩放份额与成本基数：`shares=(hShares*dayPrice)/nav`、`buyNetValue=nav*(holdingBuyNetValue/dayPrice)`。旧实现 `shares=buy.amount/nav, buyNetValue=nav` 会强行把成本基数归到 nav，导致批量导入带历史盈亏时累计/市值被晚上净值清零。
- `holding.ts refreshEstimates` 与 `useFundValuation.reconcileHoldingFromTodayBuy` 的调用：在 `updateTradesByCode` 重算交易【之前】取买入交易原始 `netValue` 作为 `dayPrice` 传入（否则交易已被改成 nav，dayPrice 失真）。两处调用方 + `holding.ts`/`useFundValuation.ts` 补 `getTradesByCode` import。

**验证**：`npx vue-tsc -b` 通过（exit 0）。node 端到端单测：
- 场景1(用户bug) 白天买价=今日估值1.97、累计=0%、buyDate=今天；晚重算 marketValue=10000、累计=0% ✅
- 场景2(批量带历史盈亏1000/10000) 白天累计=11.11%；晚重算 marketValue_n=10000、累计_n=11.11%（不被清零）✅
- 场景3(单加) 白天/晚累计均=0%、marketValue_n=10000（无回归）✅

**副作用/注意**：盘前无估值缓存的极端边角仍会回落上一期净值（与单加同口径，可接受）；批量导入填了「持仓市值+盈亏」时成本基数会跨夜保留，符合用户导入既有持仓的意图。

## 二次修正：批量导入 = 导入既有持仓，用实际净值 + 买点画净值日，永不重算（用户 9.22 晚澄清）

用户澄清：之前记错了。**批量导入的设计本就是「导入实盘账户已有持仓」（有市值有盈亏）**，与「今天新买」完全不同：
- 批量导入用**实际已公布净值**（`accurateData.nav`）算成本/份额，`buyDate`=该净值日期 → 盘中导入用**昨天净值、买点画上一交易日**；净值更新后导入用**今天净值、买点画今天**。
- **绝不标记 estimated、绝不被 getTodayFirstBuyCorrection 重算**，历史盈亏必须保留。
- 这与「单加/加仓（今天新买，白天用估值、买点画今天、晚上重算为净值）」是两套逻辑，不能混。

**改动（9.22 晚）**：
- `Holding.vue batchImport` 回退到上述「实际净值 + navDate」逻辑：买价=`accurateData.nav>0?nav:1`、`estimated=false`、`buyDate=navDate`、交易 `date=navDate`。移除 `resolveAddValue` 调用与临时 `const today`；`getCalendarDateStr` import 因 batch 不再用、且 submitForm 也不用时已删（submitForm 仍用 `resolveAddValue`）。
- `useFundTrade.getTodayFirstBuyCorrection` 新增守卫 `if (!buy.estimateAtTrade) return null`：
  - `estimateAtTrade` 仅在 `createTrade` 的 `estimated` 为真时写入（`createTrade` line 66）；`updateTradesByCode` 不清除它。
  - 批量导入 `estimated:false` → `estimateAtTrade` 恒空 → 即使 `buyDate===today`（更新后导入的边角）也**永不重算**，历史盈亏保留。✅
  - 单加-盘中估值：`estimateAtTrade` 有值 → 仍正常重算 ✅；单加-更新后买（estimated:false）→ 本就无需重算，跳过为 no-op ✅；加仓（buys.length≠1）仍排除 ✅。
  - 此守卫比单纯看 `estimated` 更稳：单加盘中单在 `updateTradesByCode` 后会把 `estimated` 翻成 false，但 `estimateAtTrade` 保留，故仍能识别为「需重算的估值单」。

**验证**：`npx vue-tsc -b` exit 0。node 仿真（sim3）：批量-盘中/批量-更新后 均 reconcileFired=false（保留原成本基数）；单加-盘中估值 reconcileFired=true（shares=33783.78,bnv=1.48）；单加-更新后/加仓 均 false。

**结论**：「权衡」段（第36行）所述"批量带历史盈亏会被清零"——**已被此守卫消除**。批量导入现在任何情况下都保留历史盈亏，符合用户设计意图。
