## 云备份→手机云恢复 金额不一致 排查

用户场景：电脑端云备份 → 手机端云恢复，账户金额对不上。
具体：华宝致远 6.49万(P)->5.49万(M)，银海海外数字 10.47万->9.87万，京东现金 11.62万->9.6万。三项同时、按比例变少。

### 结论
- **不是手机端计算 bug，也不是备份文件"存错了"**——现金(`panoramaAccountCash`)不经任何计算，PC 显示值 = `getPanoramaAccountCash()`(`PanoramaDashboard.vue:382`)，备份抓的也是同一个值(`BackupActions.vue:162`)，还原整对象覆盖(`savePanoramaAccountCash`)。只要备份里是 11.62，手机必显 11.62。手机显 9.6 ⇒ 备份那刻就是 9.6 ⇒ **手机恢复到的 gist 不是电脑端最新那份**（电脑端这次云备份没成功覆盖 gist / 静默失败 / token 不同 / findBackupGist 匹配到旧 gist）。
- 三项差值比例各异(−15.4%/−5.7%/−17.4%)且现金也少，唯一合理解释是"恢复到更早的旧备份"（用户近期交易后的状态没进 gist）。

### 修掉的两个真实代码缺陷
1. `src/components/BackupActions.vue` `applyBackupData` 顺序错误：`initHoldings()`(联网重算估值+自愈)原本在 `trades/cash/dcaPlans/fundNetValues` 写回之前跑，导致①自愈补齐买点用恢复前旧交易②净值快照在网络重算后才落盘(恢复瞬间市值由手机联网决定)③定投幂等依赖的恢复后 dcaPlans 缺失。已改为**先写回全部数据、最后再 `initHoldings()`**，并加恢复后现金逐账户一致性校验(`console.warn`)。
2. `src/api/gist.ts` `findBackupGist` 模糊匹配('fund'/'backup'/'持仓' + 描述)返回第一个命中，且 create/update 分两套逻辑——可能写到一个 gist、读到另一个。已改为**精确文件名 `fund-holdings-backup.json` 优先**，兜底才用描述匹配（排除定投云端同步 gist）。

## 续：定投状态栏显示"本地"徽标（云端协调未生效）

用户确认数据已一致后，发现定投状态栏显示"本地"徽标（应为"云端"）。

### 结论
- "本地"徽标 = `executeDueDCAsCloud` 返回 `cloudCoordinated:false`，即 DCA 走了**纯本地兜底**（`dcaCloud.ts` 的 `readDcaCloudState` 返回 null → `dca.ts` `!cloud` 分支直接本地执行）。**跨设备"只扣一次"保护此时是关闭的**——若 PC/手机同一天都跑 DCA 可能重复扣款。
- **与备份成功与否基本独立**：备份/恢复用的是主 gist `fund-holdings-backup.json`；DCA 云端协调用的是**另一个独立 gist** `dca-sync.json`(描述"定投计划云端同步")。两者都需 GitHub Token，所以"备份能成功≠DCA 云端能成功"，但 token 缺失会同时影响两者。
- 最可能成因：**PC 与手机配置了不同的 GitHub Token**（或手机端 token 无 gist 权限）→ 手机读不到 PC 建的 dca gist → 本地兜底。需用户确认两端是否同一 token。

### 修掉的代码缺陷（真 bug）
- `dca.ts` `executeDueDCAsCloudCore` 的 `!cloud` 分支：云端状态 gist 不存在时直接走本地执行，**且后续 writeDcaCloudState 只在 cloud 非空分支调用 → gist 永远不被创建 → 新 Token 永久卡"本地"**（引导死锁）。
- 修复：`findDcaGist` 改为三态（找到/notfound/error）；`readDcaCloudState`/`writeDcaCloudState` 区分处理；新增 `bootstrapDcaCloudState(plans)`，仅在 findDcaGist 明确 `notfound` 时创建 gist（error/已存在不重复建，避免覆盖台账/误建重复 gist）；`!cloud` 分支先尝试引导+重读，失败才退回本地。`cloud` 声明由 const 改 let。
- `npx vue-tsc -b` 退出码 0。

## 续2：定投徽标"又变本地"——瞬时 GitHub 失败的误翻（已修）

用户反馈：数据一致后，定投状态栏又显示"本地"。

### 根因（徽标会"闪"到本地）
- 徽标由 `executeDueDCAsCloud` 写进 localStorage 快照 `dca_today_sync.cloud`（`dca.ts:667`，每日覆盖），反映**本设备最近一次 DCA 执行**结果。
- `executeDueDCAsCloud` 在**每次页面挂载 + 每 60s 自动刷新**都跑（Home.vue:943/1475/1517/1605、PanoramaDashboard:899/931、DCAPage:397、MobileDCAPage:249）。
- 老 `readDcaCloudState(0)` 把"gist 不存在"和"GitHub 读取失败(网络抖/429限流/鉴权瞬时)"**都归一成 null** → 代码走 `!cloud` 本地分支 → 写入 `cloud:false` → 徽标被钉在"本地"，直到某次干净执行才翻回。本次会话期间反复出现 `429 too many requests`，证明 GitHub 限流真实发生，是瞬时失败的主因。

### 修复（`src/api/dcaCloud.ts` + `src/utils/dca.ts`，`vue-tsc -b` 通过）
- 新增 `readDcaCloudStateEx(ttl)`：返回 `{ state, notfound, error }` 三态，区分"确实不存在"与"读取瞬时失败"。
- 核心 `executeDueDCAsCloudCore`：仅当 `probe.notfound` 才走引导创建；若因 `probe.error`(瞬时失败)进不来云端分支，**本地仍兜底执行但保留上一次快照的 cloud 标记**（不翻成"本地"），并 `console.warn` 便于定位。真·本地仅限"无 token / 确实无 gist 且引导失败"。

### 提示
- 此修复避免"限流误翻本地"，但**跨设备去重仍要求两端同一 GitHub Token**——不同 token 仍是各记各的账（根因见上节）。若用户还想在瞬时失败时彻底不改写徽标之外的提示，可后续在状态栏加"云端协调已开启（去重生效）"明确文案。

### 实现（`src/utils/dca.ts` + `Home.vue` + `PanoramaDashboard.vue`，`vue-tsc -b` 通过）
- 新增每日标记 `dca_cloud_done`（localStorage，按 `YYYY-MM-DD` 换日失效）+ `isDcaCloudDoneToday` / `markDcaCloudDoneToday`。
- `executeDueDCAsCloud(todayStr, opts?)` 新增 `force` 选项：
  - 默认（force=false）：若 `isDcaCloudDoneToday` 为真，**直接短路返回本地快照**，不再打 gist；
  - 核心跑完后，**只有 `cloudCoordinated && deferred===0`（执行/恢复/确认无到期）才 `markDcaCloudDoneToday`**；唯独"其他设备认领中(deferred)"不标记——本机需继续轮询等对方 done 后再恢复（否则会漏恢复对端的扣款）。
- 调用方：`Home.vue` 60s `refreshData` 保持默认（被门控）；手动下拉 `onRefresh` 改 `force:true`（用户主动要同步仍可强制跑）；`PanoramaDashboard` 刷新改 `force: forceRefresh`（手动 ↻ 强制、60s 自动与挂载走门控）。DCAPage/MobileDCAPage 挂载默认（门控，省请求）。

### 注意点（告知用户）
- 标记后，**当日中途新增定投计划**不会被 60s 自动刷新捡到，需手动下拉刷新（force）才会执行——这是"一天一次、少打 gist"的取舍。
- 换日自动失效，次日正常重新跑。

### 根因
- 对钩出现 = `markDcaCloudDoneToday` 已置位（终端态 `cloudCoordinated && deferred===0`），说明门控**确实生效**（不再打 gist）。

### 修复（`src/utils/dca.ts`，`vue-tsc -b` 退出码 0）
- 短路分支 `recovered` 由 `prev.recovered` 改为 `0`（executed/skipped 本就是空数组）。状态条不依赖此返回值，清零安全。
- 顺带确认：真实恢复路径（Core 内 `applyCloudExecution`）本就幂等（只返回"新应用"笔数），手动 force 拉取不会重复弹；弹窗只来自被门控的自动刷新返回值，根因即此。

## 续8：手机端点「定投」跳转报 Failed to fetch dynamically imported module

用户报错：`goDca`(Holding.vue:117) 跳 `/m/dca` 时浏览器抛 `TypeError: Failed to fetch dynamically imported module: .../MobileDCAPage.vue`（router.ts:88 的动态 import）。

### 结论（已用独立 Vite 实例验证）
- 源码无问题：另起 `vite --port 5174` 用 curl（带 `NO_PROXY=localhost,127.0.0.1` 绕开本机 58251 代理）直接拉取 `MobileDCAPage.vue` 与 `dca.ts` 的 transform 产物，均 `HTTP 200`、合法 JS、无 error 标记。`vue-tsc -b` 也通过。
- 真因 = **用户正在跑的 5173 dev server 模块图处于陈旧/损坏态**（本会话多次用工具直接改文件，Vite HMR 没干净接管，依赖图错乱），导致该动态 import 拉到的模块不可实例化 → 浏览器报 fetch 失败。并非代码 bug。

### 解决（交给用户操作）
- 停掉并重启 `npm run dev`（或对应启动命令），再浏览器硬刷新（Cmd/Ctrl+Shift+R）。重启会重新预构建+重建模块图，陈旧态消失。
- 验证手法备忘：本机有 HTTP(S)_PROXY=127.0.0.1:58251 透明代理，curl localhost 必须 `NO_PROXY=localhost,127.0.0.1` + `--noproxy '*'`，否则会 502/connection refused 误判。
