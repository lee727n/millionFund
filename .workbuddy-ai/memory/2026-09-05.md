## 修复：做T记录（fund_t_trades）在版本更新时被清空

**现象**：用户反馈做T记录全部消失，K线图紫色标记和 TradeCenter 的 T交易区块都空了。

**根因**：`src/utils/storage.ts` 的 `checkVersionAndClearCache()` 在版本变更时清理缓存：
- 清理规则 = key 命中 `CACHE_PREFIXES`（`fund_`/`api_`/`market_`/`estimate_`）**且不在** `preservedKeys` 白名单
- `T_TRADES = 'fund_t_trades'` 以 `fund_` 开头会命中前缀，但当初加做T功能时（commit 8743b76「标记T」）**漏登记进白名单**
- 结果每次 APP 版本更新，`fund_t_trades` 被 `removeItem` 删掉

**修复**：把 `STORAGE_KEYS.T_TRADES` 加入 `preservedKeys`，并补注释警告「新增存储 key 必须同步白名单」。

**教训/约定**：所有以 `fund_` 等缓存前缀开头的**用户数据** key，必须登记进 `preservedKeys`，否则会被版本更新误删。当前白名单已覆盖：watchlist / holdings / trades / t_trades / net_values / source_filter / app_version / starred_funds。

**验证**：`npx vue-tsc --noEmit -p tsconfig.app.json` 通过，无错误。

**数据恢复提示**：Holding.vue 的本地导出和 GitHub Gist 云端备份都含 `tTrades: getTTrades()`；云端恢复也会在 `jsonData.tTrades` 存在时调用 `saveTTrades(jsonData.tTrades)`。若用户在做T记录被清除前成功执行过云端备份，Gist 理论上可以恢复。之前误判为 Gist 只存持仓，已纠正。

## dataSource 误标修复（用户已确认，已改）

决策链 `isWeekday && !isNavUpdated && nav > 0 && !inTradingTime`（盘前）分支用 `result.nav` 做 currentValue，却把 `dataSource` 标成 `'estimate'` → 已改为 `'nav'`。

**连带修复（关键）**：改完发现会打掉一处安全网。Detail.vue / TradeCenter.vue 在拉完数据后有：
```
if (data.dataSource !== 'nav' && !holdingConfirmedUpdated) { 把今天的交易恢复为 estimated:true }
```
而前面 `updateTradesByCode(code, data.nav, data.navDate)` 会无条件把 `estimated` 的交易用「上一期净值」确认掉（`shouldUpdate = t.estimated || t.date === navDate`，确认后 `estimated=false`）。**这个 guard 就是唯一的兜底**。dataSource 改成 'nav' 后 guard 会被跳过 → 今天的交易被昨天的净值错误确认、份额算错。

**解法**：给 `FundAccurateData` 新增 `navIsCurrent: boolean`（= 函数内已算好的 `isNavUpdated`，即 navDate 是今天 / QDII 的前一工作日），两处 guard 改用 `!data.navIsCurrent`。这样各分支行为完全不变，唯独盘前分支保住了安全网。周末分支（navDate=周五）也会因此把今天的交易恢复为 estimated，属更正确的行为。

**教训**：`dataSource` 表达的是「currentValue 用的是哪类数据」，不能反推「净值是否已更新」。要判断后者必须看 `navIsCurrent`。

改动文件：`src/api/fundFast.ts`（接口 + 函数）、`src/views/Detail.vue`、`src/views/TradeCenter.vue`、`src/stores/holding.ts`（补 `navIsCurrent: true`）。`npx vue-tsc -b` 退出码 0。

## 估值取数统一编排：架构评估（仅评估，未改代码）

用户提出抽 `AutoFetchFundValue` 统一做「判断净值是否更新 → 取历史净值 → 取/算估值 → 选值」，要求先评估。

**结论：方向对，但必须满足四条约束**

1. 返回值要是**显式决策结果** `FundValueResult { value, isNav, navIsCurrent, nav, navDate, estimate, dayChange }`，调用方禁止再写 `dataSource === 'nav'`。「净/估」读 `isNav`，「今天交易能否确认」读 `navIsCurrent`。
2. `updateTradesByCode` + 「!navIsCurrent 就把今天交易恢复为 estimated」这条安全网必须留在编排函数**内部**且顺序不变，不能只取数不校正。
3. `holding.isUpdated` 仍要在 store 里由 `navDate` 重算，**不能信任传入的 navIsCurrent**（快路径合成的 data 里恒为 true → 自己证明自己 → 永不调 API → 跨天不自校正）。
4. 日期口径统一用 `getTradingDateStr()`，禁止调用方再 `new Date().toLocaleDateString('en-CA')` 比日期。

**现状：同一决策 7 文件 4 套写法**（已造成过 dataSource 那次事故）
- A. `dataSource==='nav' && nav>0` 三目：useFundValuation.ts:102、TradeCenter.vue:260、aiAnalyzer.ts:393、Detail.vue:56
- B. 三分支 + 日期兜底：Detail.vue:301-332、Home.vue:529-548（else 里再 `navDate === today` 判一次）
- C. 二分支 + `estimate || currentValue`：PanoramaDashboard.vue:472-482（无日期兜底，v>0 才写回）
- D. 展示用 `dataSource==='nav' ? '净':'估'`：PanoramaDashboard.vue:877/952/1027/1098、FundGridItem.vue:245、MiniKLineChart.vue:350、Detail.vue:1093/1097

**额外发现**：`toLocaleDateString('en-CA')` 全项目 21 处（Detail 6 / Home 7 / Panorama 4 / Holding 2 / TradeCenter 1 / ScreenshotImport 1），与 `getTradingDateStr()`（9 点前算昨天）口径不一致 → 早上 8 点开交易弹窗时主分支与日期兜底分支结论可能相反。

**命名建议**：改叫 `resolveFundValue` / `useFundValue`——它其实是「解析」不是「抓取」，缓存命中时不发请求；`Auto` 前缀易与自动刷新混淆。

**建议迁移顺序**：① 先加 `FundValueResult` 类型并让 `fetchFundAccurateData` 内部填 `value/isNav`（保留旧字段，向后兼容，零风险）→ ② 改 Home/Detail 交易弹窗 → ③ 改 PanoramaDashboard → ④ 改 TradeCenter/aiAnalyzer/MiniKLineChart/FundGridItem 展示分支。

另：`useFundValuation.getFundData` 已导出但全项目无调用。
